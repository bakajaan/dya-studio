# DYA Studio 改善提案

リポジトリ全体(ソースコード・テスト・CI/CD・ドキュメント)を分析した結果に基づく、サービス改善の提案集です。優先度別に整理しています。

## 現状サマリ

DYA Studio は、ZMK ファームウェアを搭載した DYA キーボード向けの Web ベース設定ツールです。

**強み(すでに良くできている点)**

- React 19 + TypeScript + Vite + Tailwind CSS v4 のモダンなスタック
- USB シリアル / WebUSB / BLE(GATT)の 3 系統の接続方式 + 実機不要の**デモモード**
- 日英 i18n、ダーク/ライトテーマ、デザインシステムのドキュメント化(`docs/DEVELOPMENT_GUIDE.md`)
- Jest によるユニットテスト(hooks / lib / 主要ページ)、GitHub Actions での CI、husky + lint-staged
- Cloudflare Pages へのデプロイパイプライン

**主なギャップ**

- 設定のバックアップ・復元手段がない(ファームウェア書き換えで設定が消えるリスク)
- タブ状態が URL に反映されず、リロード・共有・ブックマークができない
- ErrorBoundary がなく、1 コンポーネントの例外でアプリ全体が白画面になり得る
- E2E テストがない(デモモードがあるのに活用されていない)
- 1,000 行超の巨大コンポーネントが複数あり、変更コストが高い
- リリースが手動トリガーのみで、PR プレビュー環境もない

---

## 優先度: 高 — ユーザー価値に直結する改善

### 1. キーマップ・設定のエクスポート / インポート(バックアップ機能)

**課題**: キーマップ、コンボ、マクロ、トラックボール設定などをファイルに書き出す手段がない。ファームウェア更新や設定リセットで作り込んだ設定が失われると、ユーザーは手作業で再構築するしかない。

**提案**:

- 全設定(キーマップ / コンボ / マクロ / センサー設定 / カスタム設定)を 1 つの JSON にエクスポート
- JSON からのインポート(復元)。バージョンフィールドを含めて将来の互換性を確保
- ホーム画面またはヘッダーに「バックアップ / 復元」導線を配置

**効果**: データ消失リスクの解消はユーザーの信頼に直結する。設定ファイルの共有はコミュニティ形成(後述の提案 12)の土台にもなる。

### 2. URL ルーティングの導入

**課題**: [App.tsx](../src/App.tsx) でタブは `useState` のローカル状態のみで管理されており、リロードすると常にホームに戻る。特定ページへのリンク共有やブックマークもできない。Google Analytics には `page_path: /${tabId}` を送っているが、実際の URL は変化しない。

**提案**: ハッシュルーティング(`#/keymap` など)を導入し、タブとURL を同期する。SPA のまま実装でき、Cloudflare Pages 側の設定変更も不要。

**効果**: リロード復帰・リンク共有・ドキュメントからの直接リンク(「トラブル時は #/health を開いてください」等)が可能になり、GA のページ計測も実態と一致する。

### 3. ErrorBoundary とエラーリカバリ UI

**課題**: ErrorBoundary が存在せず、ページ内の例外(例: デバイスからの想定外レスポンス)でアプリ全体がクラッシュする。ハードウェア相手のツールは不確定要素が多く、この影響が大きい。

**提案**:

- ルートとタブ単位に ErrorBoundary を設置。タブ内エラーは該当タブのみのエラー表示に留め、他機能は使い続けられるようにする
- 「再試行」「再接続」「問題を報告(GitHub Issue リンク)」の導線を用意

### 4. 非対応環境の事前検出と案内

**課題**: WebUSB / Web Bluetooth は Chromium 系ブラウザ限定。Firefox / Safari ユーザーは接続ボタンを押して初めて失敗を知る。README に記載はあるが、アプリ内での案内がない。

**提案**: 起動時に `navigator.usb` / `navigator.bluetooth` / `navigator.serial` の有無を判定し、非対応環境ではスプラッシュ画面([SplashScreen.tsx](../src/components/SplashScreen.tsx))に「対応ブラウザ(Chrome / Edge)をお使いください。デモモードはこのままお試しいただけます」と表示する。Linux の udev ルール設定などの OS 別トラブルシューティングへのリンクも添える。

**効果**: 新規ユーザーの最初のつまずきを解消する。デモモードへ誘導することで、非対応環境でも製品の魅力を伝えられる。

## 優先度: 中 — 品質と開発速度を上げる改善

### 5. デモモードを使った E2E テスト

**課題**: ユニットテストはあるが、「接続 → 設定変更 → 保存」のようなユーザーフロー全体を検証するテストがない。実機が必要なため難しい、と思われがちだが、本プロジェクトには完成度の高いデモトランスポート([src/lib/transport/demo.ts](../src/lib/transport/demo.ts) ほか一式)がすでにある。

**提案**: Playwright を導入し、デモモードで主要フロー(接続、キーマップ編集、マクロ作成、言語切替、テーマ切替)を CI で回す。

**効果**: リグレッションを実機なしで検出できる。特にトランスポート層やプロトコル更新(`buf generate` 由来のコード変更)の安全網になる。

### 6. 巨大コンポーネントの分割

**課題**: 変更頻度が高いファイルが肥大化している。

| ファイル                                                                | 行数  |
| ----------------------------------------------------------------------- | ----- |
| [TrackballPage.tsx](../src/pages/TrackballPage.tsx)                     | 1,084 |
| [MacroPage.tsx](../src/pages/MacroPage.tsx)                             | 1,083 |
| [useRuntimeInputProcessor.ts](../src/hooks/useRuntimeInputProcessor.ts) | 965   |
| [ComboPage.tsx](../src/pages/ComboPage.tsx)                             | 863   |
| [useKeymap.ts](../src/hooks/useKeymap.ts)                               | 836   |
| [KeycodeSelector.tsx](../src/components/KeycodeSelector.tsx)            | 820   |

**提案**: ページをセクション単位のサブコンポーネントに分割し、ロジックはカスタムフックへ抽出する。まず今後も機能追加が見込まれる MacroPage / TrackballPage から着手する。

**効果**: レビュー・テスト・AI エージェントによる変更がしやすくなり、機能追加の速度が上がる。

### 7. i18n 運用の仕組み化

**課題**: [translations.ts](../src/i18n/translations.ts) は 644 行の単一ファイルで、翻訳キーは英語文そのもの。キーの追加漏れは実行時まで気づけない(直近のコミット履歴にも日本語ラベル修正が複数ある)。

**提案**:

- 未翻訳キー・未使用キーを検出するスクリプトを追加し、CI で実行する
- ファイルをページ/機能単位に分割する
- 開発時のみ、翻訳が見つからないキーを `console.warn` する

### 8. テストカバレッジの CI ゲート化

**課題**: `npm run test:coverage` は用意されているが、CI に閾値がなくカバレッジ低下に気づけない。

**提案**: `jest.config.ts` に `coverageThreshold` を設定し(現状値ベースで開始し段階的に引き上げ)、CI でカバレッジレポートを PR コメントに出す。

## 優先度: 中 — 運用・成長のための改善

### 9. PR プレビューデプロイ

**課題**: UI 変更のレビューはローカルで動かすしかない。UI 中心のプロジェクトなのでレビューコストが高い。

**提案**: Cloudflare Pages のプレビューデプロイを PR ごとに作成する workflow を追加(既存の [release.yml](../.github/workflows/release.yml) の構成を流用可能)。デモモードがあるため、レビュアーは実機なしで動作確認できる。

### 10. リリースの自動化とバージョン表示

**課題**: リリースは `workflow_dispatch` の手動実行のみ。`package.json` の version は `0.0.0` のままで、デプロイされているのがどの時点のコードか、ユーザーにも開発者にも分からない。

**提案**:

- Git タグ push でリリースを自動実行し、GitHub Release にチェンジログを生成
- アプリのフッターまたは設定画面にバージョン(またはコミットハッシュ)を表示
- 問い合わせやバグ報告時にバージョンを特定できるようにする

### 11. クライアントエラーの可視化

**課題**: 本番でユーザーがどんなエラーに遭遇しているか把握する手段が GA のイベントしかない。ハードウェア・ブラウザ・ファームウェアの組み合わせ問題が起きやすい領域なのに、再現情報が集まらない。

**提案**: Sentry(無料枠で十分)等のエラートラッキングを導入し、ErrorBoundary(提案 3)からも捕捉エラーを送信する。個人情報やキー入力データを送らないよう、送信対象は例外情報とブラウザ情報に限定する。

### 12. キーマップ共有・プリセット機能

**課題**: DYA キーボードのユーザーが増えたとき、「他の人の設定を参考にしたい」というニーズに応える仕組みがない。

**提案**(段階的に):

1. エクスポート機能(提案 1)の JSON をベースに、リポジトリ内に公式プリセット集(`presets/`)を用意し、アプリから 1 クリックで適用できるようにする
2. 将来的には URL エンコードした設定の共有リンク生成へ拡張

**効果**: 新規ユーザーのセットアップ体験が大きく向上し、コミュニティの活性化にもつながる。

## 優先度: 低 — 中長期の検討事項

### 13. PWA 化(オフライン対応)

静的サイトなので Service Worker の追加でオフライン動作が可能。キーボード設定ツールはネット接続と無関係に使いたい場面(外出先など)があるため相性が良い。インストール可能にすることでネイティブアプリ的な使用感も得られる。

### 14. アナリティクスのプライバシー配慮

[index.html](../index.html) で Google Analytics を無条件にロードしている。EU 圏のユーザーを考慮するなら、同意バナーの追加、またはプライバシー重視のカウンタ(Cloudflare Web Analytics 等)への移行を検討する。フッターにプライバシーポリシーページ(収集内容の明記)を置くだけでも信頼感が変わる。

### 15. 未実装ビヘイビアの対応

[behaviorMetadata.ts](../src/lib/behaviorMetadata.ts) に TODO が残っている: Key Toggle / RGB Underglow / Backlight / Power management / Soft off。DYA のハードウェア構成で意味のあるものから順次対応する。

### 16. 低バッテリー通知

バッテリー履歴表示はすでにあるので、閾値を下回ったときに Web Notifications API でデスクトップ通知を出すオプションを追加する。分割キーボードは片側だけ電池切れになりがちで、実用的な価値が高い。

## 推奨する着手順

| 順序 | 提案                       | 理由                                       |
| ---- | -------------------------- | ------------------------------------------ |
| 1    | #1 エクスポート/インポート | ユーザーのデータ保護。他機能(#12)の土台    |
| 2    | #3 ErrorBoundary           | 実装が小さく、体験悪化の最大リスクを塞げる |
| 3    | #4 非対応環境の案内        | 新規ユーザーの離脱防止。実装が小さい       |
| 4    | #2 URL ルーティング        | UX と計測精度の両方が改善                  |
| 5    | #5 E2E テスト              | 以降の改善(#6 分割など)の安全網になる      |
| 6    | #9 PR プレビュー           | 開発サイクル全体が速くなる                 |

以降は #6(分割)→ #10(リリース自動化)→ #12(プリセット)の順を推奨します。
